# Guía para contribuir a BOX-IT

[← Inicio](README.md) · [Documentación](docs/README.md) · [Issues](https://github.com/Wilder-reyes/BOX-IT-CAJATHON-2026/issues)

Este repositorio público sirve para **organización y preparación**, no para publicar el enunciado reservado del desafío.

## 1. Antes de empezar

1. Revisa el [README](README.md) y el [roadmap](docs/02-organizacion/ROADMAP-PREPARACION.md).
2. Elige o crea un [Issue](https://github.com/Wilder-reyes/BOX-IT-CAJATHON-2026/issues) con un objetivo verificable.
3. Confirma responsable y revisor. No asumas que el coordinador es el líder del equipo.
4. Mantén en un canal autorizado cualquier dato personal, confidencial o restringido.

## 2. Trabajo con Git

| Tipo de cambio | Ejemplo de rama |
|:--|:--|
| Documentación | `docs/guia-de-validacion` |
| Organización | `chore/mejora-de-plantillas` |
| Corrección | `fix/enlace-documentacion` |
| Funcionalidad del reto (cuando exista) | `feat/funcionalidad-autorizada` |

- Commits breves: `docs: organiza índice de bases`.
- Pull Request con el **por qué**, el **qué**, la **evidencia** y un Issue relacionado.
- Solicita revisión a una persona distinta de quien hizo el cambio.
- Evita cargar archivos binarios grandes, dependencias instaladas o credenciales.

## 3. Definición de terminado

- [ ] El entregable responde al Issue.
- [ ] Incluye fuentes y fechas cuando usa información externa.
- [ ] Se puede revisar o ejecutar según corresponda.
- [ ] Está clara la diferencia entre hechos, hipótesis y estimaciones.
- [ ] No revela información restringida.
- [ ] Declara componentes preexistentes, titulares y licencias si aplican.
- [ ] Recibió una revisión cruzada.

## 4. Reglas particulares del Cajathon

Según las bases, en la etapa final debe evidenciarse la construcción de funcionalidad crítica **nueva o adaptada sustantivamente durante el evento**. Preparación y herramientas previas pueden reutilizarse si se identifican y respetan derechos.

No se define producto específico mientras no se comunique el desafío oficial.

## 5. Dónde colocar documentos

- `docs/01-bases/`: requisitos y criterios de evaluación.
- `docs/02-organizacion/`: reuniones, roadmap, decisiones, stack propuesto.
- `docs/03-activos/`: registro de componentes preexistentes.
- `docs/04-solution-concept/`: plantillas para el concepto oficial.
- `docs/05-evidencias/`: pruebas y trazabilidad.
- `docs/06-informes/`: investigación y entregables individuales.

El seguimiento vive en GitHub Issues, no en copias paralelas de tareas dentro del código.
